# Meeting tracker ↔ Tasks ↔ Microsoft Teams — implementation report

This document describes **how the current codebase models meetings and tasks**, what gaps block “direct” integration, and a **phased plan** to connect the Meeting tracker to central task management and, later, to **Microsoft Teams / Outlook calendar** via Microsoft Graph.

---

## 1. Current state (as implemented)

### 1.1 Meetings (`platform_meetings`)

- **Model:** `Meeting` in `backend/db/database.py` — title, type, dates/times, organizer, project, MoM fields, etc.
- **API:** `backend/routers/meetings.py` — CRUD under `/meetings`, gated by `require_vertical("meetings")` and project scope (`allowed_project_ids`, `assert_project_access`).
- **UI:** `frontend/src/pages/Meetings.tsx` — “Log meeting”, table, search.

### 1.2 Meeting action items (`meeting_action_items`)

- **Model:** `MeetingActionItem` — `meeting_id`, `description`, `owner` (**free-text**, not `user_id`), `due_date`, `status`, `sort_order`.
- **Important behavior:** On `PATCH /meetings/{id}`, when `action_items` is sent, `_apply_meeting_body` does `m.action_items.clear()` and **re-appends new rows**. That means **database IDs of action items are not stable across edits**. Any integration that stores `meeting_action_items.id` in `platform_tasks` without changing this pattern will **break links** after the user saves the meeting form again.

### 1.3 Central tasks (`platform_tasks`)

- **Model:** `Task` — `title`, `description`, `status`, `priority`, `due_at`, `project_id`, **`linked_resource_type`**, **`linked_resource_id`** (string), `meta_json`, plus `TaskAssignee` for real users.
- **API:** `backend/routers/tasks.py` — `/tasks`, gated by `require_vertical("tasks")` and task scope rules.

**Conclusion:** MoM “action items” and **platform tasks** are **siblings today**, not linked. Tasks already have the right **extension points** (`linked_resource_*`, `meta_json`) to point back to a meeting (and optionally a stable line identifier).

## 2. Target integration: meetings → tasks

### 2.1 Product behaviour (recommended)

| Capability | Description |
|------------|-------------|
| **Promote / sync** | From a meeting (save or explicit control), create or update `Task` rows for each action item that should appear on the **Tasks** page. |
| **Single execution surface** | Day-to-day status, assignees, and reminders live on **Tasks**; the meeting row remains the **MoM source** (narrative + audit). |
| **Project + RBAC** | Copy `Meeting.project_id` onto `Task.project_id` so existing task visibility matches meeting scope. |
| **Assignees** | Map `MeetingActionItem.owner` to `TaskAssignee` only when the owner resolves to a **user id** (picker or email match); otherwise keep owner text in `Task.description` or `meta_json`. |

### 2.2 Data model options

**Option A — Link from task only (minimal schema change)**  
- On sync, set e.g. `linked_resource_type = "meeting"`, `linked_resource_id = str(meeting.id)`, and in `meta_json` store `{ "action_line_key": "<stable key>" }` where `action_line_key` is generated by the client (UUID) or derived from a **new** optional column on `MeetingActionItem` (see Option B).

**Option B — FK from action item to task (clearest)**  
- Add nullable `task_id` on `MeetingActionItem` (FK → `platform_tasks.id`, `ON DELETE SET NULL`).  
- Sync: upsert task, set `action_item.task_id`.  
- Tasks list can join or filter by `linked_resource_type` / `meeting` for reporting.

**Option C — Stable action line id (required if you keep clearing children)**  
- Add `client_stable_id` (UUID) on `MeetingActionItem`, returned to the UI and sent back on save; change `_apply_meeting_body` to **upsert by `client_stable_id`** instead of `clear()` + append-only new rows **or** match existing rows by id when `id` is present in the payload.

**Strong recommendation:** Combine **B + C** (or A + C): **stable line identity** + explicit **task link**, so edits to the MoM do not orphan tasks.

### 2.3 Backend services (sketch)

1. **`sync_action_items_to_tasks(db, meeting, user)`**  
   - For each action item with a stable key: find `Task` by `linked_resource_type/id` + key in `meta_json`, or by `MeetingActionItem.task_id`.  
   - Create/update: title from first line of `description`, `due_at` from `due_date`, map status with a small vocabulary map (MoM strings → `open` / `in_progress` / `done`).  
   - Resolve assignees; enforce `assert_project_access` and task-assignee rules like `_validate_manager_assignees`.

2. **Hooks**  
   - Call from `create_meeting` / `patch_meeting` after commit **or** from a dedicated `POST /meetings/{id}/sync-tasks` to avoid surprising users on every autosave.

3. **Reverse sync (optional)**  
   - On `PATCH /tasks/{id}` when `linked_resource_type == "meeting"`, update the corresponding `MeetingActionItem.status` / dates if you want the MoM table to reflect task completion. **Guard** with permissions (same project, meetings vertical).

### 2.4 Frontend

- **Meetings form:** Per action row: “Create task” / “Linked to task #123” with deep link to `/tasks` (or drawer).  
- **Tasks page / filters:** Filter `linked_resource_type === "meeting"` and show meeting title from `meta_json` or a lightweight `GET /tasks?linked_meeting_id=`.

## 3. Microsoft Teams / Outlook calendar (future)

Teams calendar events are exposed through **Microsoft Graph** (generally as **Outlook calendar events**, often with `onlineMeeting` for Teams).

### 3.1 Auth model

| Approach | Use when |
|----------|----------|
| **Delegated (per user)** | Each user links their Microsoft work account; you store refresh tokens (encrypted). Events appear as **that user** in Teams/Outlook. Fits “my calendar”. |
| **Application (app-only)** | Service principal reads/writes calendars you’ve granted org-wide. Heavier admin consent; good for **tenant-wide sync bots**, not typical for first version. |

For “connect to MS Teams calendar” in a governance app, **delegated OAuth** is usually the right first step.

### 3.2 Useful Graph APIs (high level)

- **List / create / update events:** `/me/calendar/events` or `/users/{id}/calendar/events`  
- **Online meeting:** create event with `isOnlineMeeting: true` to get a **join URL**  
- **Change notifications (webhooks)** or **delta query** on calendar folders for incremental sync  
- **Optional:** Teams-specific endpoints if you need channels / tabs later

### 3.3 Mapping to your `Meeting` entity

| Platform field | Graph / Teams direction |
|----------------|-------------------------|
| `meeting_title`, `meeting_date`, `start_time`, `end_time` | `subject`, `start` / `end` (dateTime + timeZone — store **IANA** or explicit offset) |
| `organizer_user_id` | Graph organizer / attendee list |
| `project_id` / account | Store in `bodyPreview` extension, **open extension**, or `categories` / custom property bag (keep under Graph size limits) |
| `mom_link_remarks` / attachments | `webLink` to Outlook, `attachments` array for small refs; large files → blob storage + URL in extension |

Add columns such as **`graph_event_id`**, **`graph_calendar_id`**, **`graph_change_key`** (for optimistic concurrency), and **`graph_sync_status`** on `Meeting` when you implement sync.

### 3.4 Sync directions (choose explicitly)

1. **Import-only:** Graph → platform “suggested meetings” or auto-fill draft `Meeting` rows (user confirms in your UI). Lowest risk.  
2. **Export-only:** “Log meeting” → “Also add to my Outlook” creates Graph event.  
3. **Two-way:** Requires conflict rules (last-write-wins, or “platform is source of truth for MoM fields only”).

### 3.5 Enterprise checklist

- Azure AD app registration, **admin consent** for required scopes (`Calendars.Read`, `Calendars.ReadWrite`, `OnlineMeetings.ReadWrite` as needed)  
- Token encryption at rest, refresh rotation, revoke on logout  
- Audit log entries (you already have `log_activity` patterns) for “created Teams event from meeting MTG-…”

## 4. Suggested delivery phases

| Phase | Scope | Outcome |
|-------|--------|---------|
| **0** | Stabilize action items (stable id / upsert) | Safe linking for any downstream integration |
| **1** | `sync_action_items_to_tasks` + UI affordances | Action items appear as real **Tasks** with correct project scope |
| **2** | Assignee resolution (user picker + email) | `TaskAssignee` populated; notifications possible later |
| **3** | Optional reverse sync task → MoM line | MoM table reflects completion |
| **4** | Microsoft Graph delegated OAuth | User can link Microsoft account |
| **5** | One-way calendar export or import | First Teams/Outlook integration path |
| **6** | Webhooks / delta | Near–real-time calendar sync |

## 6. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Action item IDs churn on PATCH | Stable keys + upsert (Section 2.2) |
| Free-text `owner` vs task assignees | User picker or controlled directory lookup |
| Duplicate tasks on re-sync | Idempotent sync keyed by `meeting_id` + stable line id |
| Teams two-way conflicts | Start one-way; document source of truth per field |
| Compliance (PII in calendar body) | Minimize body text; keep detail in platform DB |
