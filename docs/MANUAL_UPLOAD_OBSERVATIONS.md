# Manual Excel upload — observations

This note records **practical observations** when loading data from **filled `excel_upload_masters` workbooks** (ORM field names in row 1, hint row 2, data from row 3) via the CLI, as opposed to the **legacy** corporate finance / SLA “Base File” pipelines.

For the **recommended load order** and relationship between template files and tables, see `excel_upload_masters/README.md`. For **all** CLI/API ingestion paths (directory, `ingest_sla` basefile, `ingest_finance` multi-sheet, etc.), see `docs/DATA_INGESTION_RUNBOOK.md`.

---

## Corporate finance master (`ingest_finance.py`) — quick facts

This path is **not** the filled `10_finance_core` workbook; it expects **multi-tab** masters (`Revenue_Budget`, `CM Actual`, `Unbilled`, …). **Authoritative detail:** `docs/DATA_INGESTION_RUNBOOK.md` §6.

- **Dates:** Prefer datetime month headers (Apr–Mar); they land on `reporting_month` unchanged. **`FY2025-26`**-style cells parse correctly when text months are used.
- **Lacs:** Values with **`0 < |x| < 2000`** are scaled by **`100_000`** (heuristic; large “Lacs” values ≥ 2000 are not scaled).
- **Gaps (FY25-26-style files):** Tabs such as **`PPC_Actual`** (cost), **`Revenue_Adjustment`**, **`Rev_Productivity_Actual`**, **`Non Taggd_Source_Joiner`** are **not** wired in `ledger_specs` / KPI specs unless extended in code.

---

## What “manual upload” means here

- **Templates** live under `excel_upload_masters/templates/` (generated by `excel_upload_masters/generate_templates.py`).
- **Filled** copies (e.g. under `actual_data/`) are ingested with a **dedicated** script that understands **table-named sheets** and `**_FK_REFERENCE` / `_project_mapping_needed`** helpers—not with:
  - `backend/scripts/ingest_finance.py` (expects sheets like `Revenue_Budget`, `CM_Actual`, …), or
  - `backend/scripts/ingest_sla.py` (expects a sheet named `**Base File**` and a different column layout; see `docs/DATA_INGESTION_RUNBOOK.md` §4 for score-column rules and API logging).

## CLI: filled master workbooks

From the **repository root**:

```bash
python3 backend/scripts/ingest_excel_master_filled_workbooks.py \
  --finance path/to/10_finance_core_filled.xlsx \
  --sla path/to/08_sla_FILLED.xlsx \
  --wfm path/to/09_workforce_management_filled.xlsx
```

Omit `--finance`, `--sla`, or `--wfm` if you only need a subset. Set `DATABASE_URL` to your target database (local Docker Postgres: `postgresql+psycopg://tgddata:tgddata_dev@127.0.0.1:5432/tgddata`, or Cloud SQL via proxy). Legacy SQLite path only if you explicitly set `sqlite:///...`.

**WFM (`09` — `wfm_hr_benchmarks`, `wfm_resource_gaps`):** the `project_id` column in the sheet holds the **account name** (string), not a numeric FK. The loader resolves names with `resolve_project_for_sla` and falls back to `get_or_create_project`. Re-importing the same file **basename** replaces prior rows with that `source_filename` (idempotent). This is **not** the legacy **`ingest_wfm.py`** **Projected HC** positional layout — the legacy path additionally fills **`sheet_metrics_json`**, **`Open Positin List`** → gaps (`uploaded_by = ingest_wfm_master`), and **`POST /wfm/upload`**; see **`docs/DATA_INGESTION_RUNBOOK.md`** §7.

The script:

- Creates or reuses `**projects**` from `_FK_REFERENCE` (and SLA `source_project_name` where needed); it does not replace a full `01_spine_clients_projects` load by itself.
- **Upserts** finance rows on natural keys where possible; **merges** SLA metric definitions and performance rows by definition id / period.
- Calls `**dedupe_finance_tables`** after finance, and `**backfill_sla_period_starts`** after SLA (same family as the rest of the app).

## Observations (finance — `10_finance_core` style)

1. **Empty `project_id` in data rows** is expected if you rely on `**_FK_REFERENCE`**: the loader maps **ledger blocks** to project **names** in FY order (FY2024-25: 69 projects × 12 months × Rev/CM/Cost; FY2025-26: 62 project blocks in file order, aligned to the 62 FY25-26 names in the reference sheet).
2. **FY25-26 monthly ledger block structure (fixed in loader, April 2026):** The sheet still has **62 x 36-row FY25-26 blocks** with no Cost rows in the first 24 rows (Revenue + Contribution Margin). Earlier we treated the last 12 rows in each block as duplicates and skipped them. The loader now handles the actual structure: rows **24:36** are **6-month halves** for additional FY25-26 projects; each pair of consecutive block tails forms one full 12-month hidden project. This recovers the missing FY25-26 projects that were previously dropped from `finance_monthly_ledger`.
3. **Cash flow and efficiency KPI** sheets were observed as **24 rows per project** where the **same 12 calendar months appear twice** in a row. The current loader imports **only the first 12 rows** of each 24-row block (one year’s worth) to avoid `UNIQUE (project_id, reporting_month)` violations and to match a single clear fiscal slice. If the second half of each block is **intended** to be a different year, the **spreadsheet should be changed** so months are not duplicated; then the script can be extended to load 24 distinct months per project.
4. **Ordering** of the 81 cash/KPI “slots” is **69 names** from `_FK_REFERENCE` (FY2024-25) **plus 12** names from the start of the FY2025-26 list. If a name is reused across FY lists, the same `project_id` may receive **successive** blocks; the loader **updates** in place. Any mismatch between that ordering and the row order in the file will attach values to the **wrong** project.
5. **openpyxl** may warn that **Data Validation** extension is not supported; reads still succeed for typical uploads.

## Observations (SLA — `08_sla` style)

1. `**metric_definitions` often have empty `project_id` in the sheet**; the loader uses `**_project_mapping_needed`** (`definition_id`, `source_project_name`, optional `project_id_TO_FILL`) to set `project_id` before inserting performance rows.
2. **Explicit `id` values (1…N)** on metric definitions are supported so imports are repeatable; performance rows are matched/upserted using `**definition_id` + `period_start`** (or legacy `reporting_month` when `period_start` is null).
3. **NaN in optional audit columns** (`system_created_at`, `uploaded_by`, etc.) is normalized on insert so SQLite datetime fields do not receive invalid values.
4. **RAG vs “Met/Not met” in the app (April 2026):** The template dropdowns store `**rag_status`** as **Green, Amber, Red**, etc. (see `excel_upload_masters/column_dropdowns.py`). The **SLA Performance** page and `/sla/*` APIs now **normalise** these to the same met / not-met / not-reported buckets (see `docs/SLA_DASHBOARD_FRONTEND_UPDATES.md` — `bucket_sla_rag`, `sla-rag.ts`). If you still see 100% “not reported” after a code update, **invalidate cache** or hard-refresh, and confirm `sla_performances` rows have non-empty `rag_status` and parseable `period_start` or `reporting_month`.
5. **FY charts (April 2026):** P1/P2 month windows in the UI follow **the months returned by** `/sla/timeseries` (derived from the latest data month), not a fixed 2024–2026 range.

## Unbilled vs revenue (UI % and “₹… Cr”)

- **App behaviour (fixed)**: The executive dashboard and `/finance/stats` now treat **unbilled** as a **point-in-time balance** per project: for each `project_id`, the **latest `reporting_month`** in the (filtered) row set is used, and those values are **summed** across projects. Sums of unbilled across **all** project–month rows **inflated** the headline (same exposure counted once per month). Collection / collection target / bad debt remain **summed** month-by-month (flow-style) unless the product is refined further.
- **Data in `actual_data/10_finance_core_filled.xlsx`**: A **spot check** still shows a few `unbilled_amount` cells on the order of **10¹²** while **revenue** `actual_value` maxes around **2×10⁷** in the same workbook. That is a **source unit/scale** problem (e.g. extra zeros, Lakhs vs full INR) in **nonzero** unbilled cells, not a display bug. Fix the sheet and re-run ingest for realistic ratios.
